Rustron v0.2 — Plan completo (GTK4 nativo)

Rustron v0.3 — Plan completo (Servo)

@27 de octubre de 2026 · @Eduardo Miranda

1. Resumen ejecutivo

Rustron es un navegador ligero para Linux, escrito en Rust y construido sobre Servo, el motor web en Rust. La interfaz también es Rust (winit + egui): sin Electron, sin WebView para la UI, sin IPC entre capas, con un solo lenguaje y un solo build.

Cambios clave respecto a la v0.2:

  • Motor: de WebKitGTK a Servo (crate servo), aislado detrás de una interfaz propia en rustron-engine.
  • UI: de GTK4 a winit + egui, el mismo camino que usa el navegador de demostración de Servo. GTK4 queda como alternativa a evaluar en la Fase 0.
  • Adblock: no existen los filtros nativos de WebKit; depende de poder interceptar peticiones en Servo (se verifica con un spike).
  • Empaquetado: sin WebKitGTK; Servo se compila con Cargo.
  • Cronograma: de 6–8 a 8–10 meses a tiempo parcial. La Fase 0 pasa a ser un spike de viabilidad con criterio de salida.

Aviso de realismo: con Servo 0.3 (junio 2026) el propio navegador de demostración todavía no sirve para uso diario, según quienes lo probaron. Muchos sitios fallarán o se verán mal. El 0.1 de Rustron será un navegador para sitios simples y para aprender, no un reemplazo de Firefox.

Propuesta de valor: un navegador 100 % Rust para Hyprland: ligero, con bloqueo de anuncios integrado y pestañas verticales estilo Zen.

2. Producto

Rustron es un navegador de escritorio real, enfocado en un nicho concreto: usuarios de Linux moderno con Wayland y gestores de ventanas tiling.

Qué es

  • Un navegador de escritorio solo para Linux.
  • Motor y UI en Rust: Servo para las páginas, egui sobre winit para la interfaz.
  • Pestañas verticales, workspaces como grupos de pestañas, modo compacto y barra de URL flotante.
  • Bloqueo de anuncios integrado, sujeto a lo que permita la API de Servo.
  • Wayland primero, X11 como compatibilidad.

Qué no es

  • No es un framework (eso es Tauri) ni una app Electron.
  • No desarrolla un motor propio: usa Servo y, si hace falta, contribuye a él.
  • No es un fork de Firefox ni de Chromium.
  • No es multiplataforma antes del 0.1.
  • No compite con Chrome; compite con servoshell, qutebrowser, Nyxt y Falkon en un nicho concreto.

Abiertas (no bloquean la Fase 0)

  1. ID de aplicación: org.rustron.Rustron u otro.
  1. Toolkit de UI: egui sobre winit (recomendado, es lo que usa servoshell) frente a GTK4 con un contexto de render fuera de pantalla mostrado en un GtkGLArea (más trabajo, sin ejemplo conocido). Se cierra en la Fase 0.
  1. Versión de Servo: LTS (solo parches de seguridad, API estable) o la última mensual (más sitios, API cambiante).
  1. Contexto de render: de ventana (WindowRenderingContext) o fuera de pantalla; depende de la UI elegida.

4. Arquitectura técnica

Rustron es un solo proceso GTK4 con dependencias que solo bajan: rustron-ui habla únicamente con rustron-core, y core orquesta cuatro servicios (motor web, adblock, almacenamiento y configuración).

[embedded content: capas de Rustron · 5 niveles]

Las flechas indican quién depende de quién; rustron-core es el único punto de contacto entre la interfaz y los servicios.

Reglas de la arquitectura

  1. Las dependencias solo van hacia abajo; ningún servicio conoce a la UI.
  1. La UI nunca toca servo: pide acciones a core y lee su estado.
  1. Toda interacción del usuario es una Action (enum) que core ejecuta; atajos, menús y botones usan el mismo camino.
  1. Servo y la UI viven en el hilo principal: Servo::spin_event_loop se llama desde el bucle de winit, activado por un EventLoopWaker. Lo que tarda (descargas, SQLite) corre en hilos aparte y vuelve por un canal.
  1. core se prueba sin ventana ni motor, con un WebBackend falso.

5. Estado y comunicación

El estado vive en estructuras Rust dentro de rustron-core; la UI las lee en cada frame y el motor las actualiza mediante eventos. No hay protocolo de mensajes ni serialización entre capas.

Modelos

TipoContenidoLo lee
Tabid, title, uri, favicon, loading, progress, can_go_back, can_go_forward, pinned, manejador del WebViewFila de pestaña, barra de URL
Workspaceid, name, color, icon, lista ordenada de TabIdSelector de workspaces, sidebar
BrowserWorkspaces, active_workspace, active_tab, cola de eventosVentana principal
AdblockStatsblocked_session, blocked_page, enabledPie de la sidebar

Eventos del motor

Los delegados de Servo (WebViewDelegate) convierten cada cambio en un EngineEvent (TitleChanged, UrlChanged, LoadStatus, FaviconChanged, NewTabRequested, Crashed, Closed, FrameReady). Browser::apply los aplica al modelo y la UI pide un redibujo. FrameReady activa WebView::paint y la presentación del frame.

Acciones

Toda operación del usuario es una variante de Action; Browser::dispatch(action) la ejecuta.

pub enum Action {
    NewTab { uri: Option<String>, workspace: Option<WorkspaceId> },
    CloseTab(TabId),
    ActivateTab(TabId),
    Navigate { tab: TabId, input: String },   // URL o búsqueda
    Reload { tab: TabId, hard: bool },
    GoBack(TabId),
    GoForward(TabId),
    SwitchWorkspace(WorkspaceId),
    MoveTab { tab: TabId, to: WorkspaceId },
    ToggleSidebar,
    ToggleCompact,
    ToggleAdblock { site: Option<String> },
    OpenUrlBar,
}

Los atajos, los botones y la paleta de comandos comparten este enum. Añadir una función es añadir una variante y su manejo, sin tocar el cableado.

Hilos y async

  • El hilo principal ejecuta winit, egui y Servo; ningún widget ni WebView se toca desde otro hilo.
  • Una pila ligera de tokio hace descargas de listas y consultas SQLite con spawn_blocking.
  • Los resultados vuelven por un canal y despiertan la UI con request_repaint.

6. Interfaz GTK4

La interfaz se dibuja con egui sobre winit, el mismo enfoque del navegador de demostración de Servo, y el contenido web lo pinta Servo en el mismo contexto de renderizado.

Jerarquía

winit::Window  (Wayland nativo)
└─ egui (un frame por redibujo)
   ├─ SidePanel izquierdo: Sidebar
   │   ├─ WorkspaceSwitcher
   │   ├─ lista de pestañas (ScrollArea + TabRow)
   │   └─ SidebarFooter (adblock, ajustes, + pestaña)
   ├─ Área central: contenido del WebView de Servo
   └─ Barra de URL flotante (egui::Area, Ctrl+L)

Decisiones

  • Render: Servo pinta el WebView con WebView::paint y el contexto de render presenta el frame; egui se dibuja encima. Cómo combinar ambos en un solo contexto es lo primero que se valida en la Fase 0.
  • Pestañas verticales: lista con favicon, título, indicador de carga y botón de cerrar.
  • Pestañas inactivas: un WebView por pestaña; al suspenderla se suelta el manejador y Servo libera sus recursos.
  • Barra de URL flotante: egui::Area centrada con sugerencias del historial; Ctrl+L la abre y Esc la cierra.
  • Sidebar: colapsable con animación de egui; el modo compacto muestra solo iconos.
  • Ventana: sin barra de título propia en Hyprland; decoraciones mínimas en otros entornos.
  • Alternativa GTK4: Servo se renderizaría fuera de pantalla y la textura se mostraría en un GtkGLArea. Es más trabajo y no hay ejemplo conocido; se reevalúa tras el spike.

7. Motor web: WebKitGTK

rustron-engine es la única capa que conoce servo: define WebBackend y WebViewHandle, y el resto del código solo ve esos tipos. Así el motor se puede cambiar o respaldar sin tocar core ni la UI.

Responsabilidades

  • Motor: ServoBuilder crea una sola instancia por proceso; Servo::spin_event_loop se llama desde el bucle de winit, despertado por un EventLoopWaker.
  • WebView por pestaña: WebViewBuilder las crea; un WebViewDelegate entrega título, URL, estado de carga, cierre y fallos (notify_crashed).
  • Navegación: request_navigation permite o bloquea; request_create_new atiende window.open y target=_blank (Servo obliga a crear la vista antes de decidir, así que se abre como pestaña nueva).
  • Render: notify_new_frame_ready pide un redibujo; WebView::paint actualiza el contexto y se presenta el frame.
  • Contenido de usuario: user_content_manager() para estilos y scripts de usuario (cosméticos del adblock).
  • Permisos, descargas y certificados: se implementan según lo que exponga la API; lo que falte se anota y se contribuye a Servo.
  • JIT: es opcional en Servo; se ofrece un ajuste para desactivarlo.

Versiones

Servo publica versiones mensuales cuya API puede cambiar y una versión LTS cada seis meses, con nueve de soporte y solo parches de seguridad. Plan: LTS para el 0.1 y una rama de desarrollo para probar lo nuevo.

Respaldo: WebKitGtkBackend detrás de un feature flag, solo si Servo no pasa la Puerta 0.

Límites que se documentan

  • Según quienes lo probaron, servoshell 0.3 aún no sirve para uso diario: la compatibilidad web es incompleta.
  • No hay extensiones de navegador y no se debe asumir soporte de DRM.
  • El rendimiento frente a WebKit y Gecko está sin medir; se mide desde la Fase A.

Fuentes: Servo 0.3, Servo embebible y LTS, API de WebView.

8. Adblock realista

Servo no tiene el formato de bloqueo de contenido de WebKit, así que el adblock depende de interceptar peticiones y de inyectar estilos; su alcance real se define con un spike antes de la Fase A.

Cómo funcionaría

  1. rustron-adblock descarga EasyList y EasyPrivacy y las guarda en ~/.cache/rustron/filters/.
  1. Las compila con adblock-rust a un motor de reglas en memoria.
  1. Bloqueo de red: cada petición se evalúa en el punto de la API de Servo que permita cancelarla. Hay que verificar en la versión elegida qué delegado lo ofrece.
  1. Cosméticos: hojas de estilo por dominio mediante user_content_manager().
  1. Las listas se actualizan en segundo plano si pasaron más de 24 h.

Capas

CapaQué haceLímite
Intercepción de peticionesEvalúa cada URL con adblock-rust y cancela las bloqueadasDepende de que Servo deje cancelar peticiones; si no, se contribuye esa API

EstadísticasContadores por página y por sesiónExactos si la intercepción es propia

Fuera de alcance en 0.1: scriptlets de uBlock, redirecciones de recursos y evasión automática de anti-adblock.

Funciones de usuario: interruptor global y por sitio, excepciones, contador y selector de listas.

Spike previo (1 semana): comprobar si un embebedor puede cancelar peticiones en Servo. Si no se puede, el 0.1 sale solo con bloqueo cosmético y el bloqueo de red queda para cuando se aporte esa API.

10. Wayland, Hyprland y GPU

Servo dibuja con WebRender y no con WebKit, así que las variables WEBKIT_* del plan anterior ya no aplican. La regla se mantiene: GPU por defecto y ningún workaround automático.

Principios

  1. El renderizado por GPU es el comportamiento por defecto; el software solo se usa de forma explícita, como diagnóstico.
  1. No se fijan variables de entorno «por si acaso»: cada una resuelve un problema concreto y puede dañar a quien no lo tiene.
  1. std::env::set_var es unsafe desde la edición 2024 de Rust: se llama una sola vez, al inicio de main, antes de crear hilos.
  1. Todo lo que se aplica queda en el log (nivel info).

Mecanismo

NivelQué haceCuándo
DetecciónLee XDG_CURRENT_DESKTOP, WAYLAND_DISPLAY y el driver de GPU; lo registraSiempre
Diagnósticorustron --diagnose imprime entorno, versión de Servo y backend de renderA petición
Perfil de renderrender = "auto" | "gpu" | "software" en config.tomlConfig del usuario
RecuperaciónSi el arranque anterior falló (marca en disco), propone el perfil seguroSolo tras un fallo
Modo software--force-software, con el contexto de render por softwareSolo a mano

Ventana y compositor: winit usa Wayland nativo; X11 queda como alternativa documentada. Las reglas de ventana y de capa de Hyprland se prueban y documentan en docs/HYPRLAND.md.

Prueba de aceptación de la Fase 0: arranca en Hyprland, carga una página y el log confirma que el render usa la GPU y no el modo software.

11. Empaquetado y CI

Flatpak es el formato principal y el AUR llega pronto, porque el público inicial usa Arch y Hyprland. Sin WebKitGTK no hay dependencia de motor del sistema: Servo se compila con Cargo y va dentro del binario.

FormatoPrioridadNotas
Flatpak1Runtime freedesktop con el SDK de Rust; sandbox y actualizaciones
AUR (rustron-git)2Comunidad Arch/Hyprland; compila desde fuentes
.deb / .rpm3Binario con dependencias de sistema mínimas (GPU, Wayland)
AppImage4Solo si hay demanda

Flatpak: puntos a verificar

  • Permisos mínimos: --socket=wayland, --socket=fallback-x11, --device=dri, --share=network, --share=ipc y la carpeta de descargas.
  • Las dependencias de Cargo se vendorizan para compilar sin red en el builder (flatpak-cargo-generator).
  • Compilar Servo es pesado en tiempo y memoria: hace falta caché en CI y comprobar la versión mínima de Rust que exija la versión elegida (Servo 0.3 se reporta con Rust 1.95).

CI (GitHub Actions)

  1. cargo fmt --check y cargo clippy -- -D warnings.
  1. cargo test para core, store, config y adblock, sin motor ni ventana.
  1. Compilación completa con caché (sccache o equivalente).
  1. Verificación de cabeceras MPL-2.0 (tarea xtask).
  1. Build de Flatpak en cada etiqueta de versión.

Las versiones de servo, winit y egui (y su integración con el contexto de render) se fijan consultando crates.io el día de la Fase 0; deben ser compatibles entre sí.

13. Roadmap

El plan avanza en cuatro fases; cada una termina en una puerta con un criterio medible y no se empieza la siguiente sin cumplirlo.

[embedded content: roadmap · 4 fases, 4 puertas]

Las fases tienen el mismo ancho en el dibujo; no están a escala.

Fase 0 — Spike de viabilidad (3–4 semanas). Responde una pregunta: ¿Servo es usable como motor hoy?

  • Workspace Cargo con rustron-app y rustron-engine mínimos.
  • Ventana de winit con un WebView de Servo que carga una página en Hyprland, con egui dibujado encima.
  • Medir: si el render usa GPU, cuántos sitios de una lista de 10 cargan bien y si el embebedor puede cancelar peticiones (adblock).
  • Cerrar dos decisiones: toolkit de UI (egui o GTK4) y versión de Servo (LTS o mensual).
  • Criterio de salida: la mayoría de los sitios simples de la lista cargan y se leen bien. Si no, se activa WebKitGtkBackend y el plan sigue con ese motor.

Después del 0.1 (sin compromiso): perfiles por workspace, importación de marcadores, sincronización cifrada opcional, paleta de comandos, estudio de Windows/macOS solo si hay demanda real.
